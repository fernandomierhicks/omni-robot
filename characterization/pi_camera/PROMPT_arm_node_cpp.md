## Goal

The arm robot runs on a Raspberry Pi 4 under `nav_profile:=pi`, the default on a Pi since Nov 2. Driving, it uses 3.6–3.9 of the Pi's 4 cores with the busiest core pinned. `arm_node` (Python, rclpy) costs **~0.5 of a core holding still at 20 Hz** (~0.67 at 50 Hz), and almost all of that is rclpy executor overhead, not arm work. Move the part of `arm_node` that runs every cycle into C++ (`omni_cpp`, like `mcu_link`, `mode_manager`, `scan_prep` and `heading_node` before it). Target: the arm under ~0.15 core holding still at 50 Hz, the tidy working as before, and the Pi's headroom while driving measured before and after.

## What is already known (Nov 2; do not re-derive)

- **Measured on the Pi and reverted, each moved nothing:** skipping depth/wrist image decoding until the task needs a frame (~1%), throttling `/arm/joint_states`, dropping the image subscriptions altogether. Lowering the cycle from 50 to 20 Hz did help (0.67 → ~0.5 core), and the tidy still binned toys (run P7). So the cost scales with wake-ups per second in rclpy, not with payloads. cProfile of the node on the Pi: `characterization/pi_camera/results/logs/H1_arm_node_profile_203309_arm_node.prof` (`PROFILE=1` in `arm_split.sh` makes another).
- Per cycle `tick()`: one SYNC_READ of six STS3215 servos (`feetech.py`, over `transport.py`: the sim's TCP bus `tcp:127.0.0.1:5763`, or a serial port on the robot), publish `/arm/joint_states` and `/tf` (base_link → each arm link from the joints, `kinematics.py`), then whoever drives sets goals (one SYNC_WRITE): `TidyTask` (`pick.py`), a `FollowJointTrajectory` goal, a named pose, or hold. Plus `/arm/state` JSON at 5 Hz, `/arm/out` at 10 Hz, `/arm/request` JSON commands, odom and camera inputs for the task.
- The tidy task (`pick.py`, `floor_vision.py`, `wrist_vision.py`: numpy, ~1,100 lines) runs a few decisions a second and on camera frames. It is not the per-cycle cost. Porting it is large and its tests are Python.

## Decide before you build (recommend first, then wait for Fernando)

Fernando wants a recommendation, with the open decisions listed, before a framework or architecture choice is executed. Lay out the options with their cost and risk, recommend one, and wait for his answer. At minimum:

1. **C++ bus-and-joints node + Python task.** C++ owns the servo bus at 50 Hz: SYNC_READ/WRITE, calibration, joint states, TF, the trajectory action, named poses, hold/relax, `/arm/out`, `/arm/state`. The Python `TidyTask` becomes a separate low-rate node that sends goals over a topic or action. Who owns the bus and who may drive must stay unambiguous (today one process owns both). The tidy's latency gets one extra hop.
2. **Whole node in C++,** the task included (Eigen/OpenCV in place of numpy). Biggest win, biggest port and parity burden.
3. **Cheaper Python first** (measure before rejecting): `rclpy`'s `EventsExecutor` (experimental in Jazzy), one timer instead of three, fewer subscriptions. Report the numbers if you try any.

## Rules that bind this work (AGENTS.md)

- Python reference cores and their `omni_cpp` twins change together; add parity tests in `ros/src/omni_cpp/test` (`test_cores.py` / `core_check.cpp`, as the catch and glue cores have) for whatever core moves: at least the STS3215 packet encode/decode and checksums, the calibration mapping (ticks ↔ rad, `drive_mode`), forward kinematics for TF, and the quintic moves if they move. Keep the cores ROS-free.
- Robot packages must not import `omni_sim`. Keep `ros/omni.sh`, the console's `supervisor.SIM_STEPS`, `launcher.ps1` and `launcher_full.ps1` consistent if launch options change. Prefer a `arm_impl:=cpp|py` style switch (as `glue:=cpp|py`), so the Python node stays available, and make `cpp` the default only after it passes.
- `config/robot_arm.json` is generated by `simulation/v11 sil/robot_export.py`; read it, never hand-edit.
- Build in WSL through `ros/omni.sh` (never on `/mnt/c`). On the Pi: `OMNI_PI=omni-cam-eth OMNI_PI_PKGS="omni_cpp omni_arm omni_bringup" bash characterization/pi_camera/pi.sh build` (sequential, `-j2`; never an unrestricted parallel build on the 4 GB Pi).
- Do not use `omni.sh stop`, `stop-console` or a broad `pkill`. Fernando's stack may be running (domain 0, ports 5761/5763, 8080/9090). `arm_split.sh` uses domain 43 and ports 5771/5773 and stops only its own processes.

## How to measure (the harness exists)

- Split run, Pi as the robot, PC as the world, over the Ethernet cable. From Git Bash: `PHASES=MANUAL,ROUTE,NAVTIDY PHASE=60 bash characterization/pi_camera/arm_split.sh LABEL arm_camera:=d435` (`NAV_PROFILE` defaults to `pi`). Per-phase CPU per process: `python ros/tools/arm_load_report.py results/pi_arm_<tag>.json results/logs/arm_load_<tag>.json`.
- **Before every `clock:=wall` run, step the Pi's clock onto WSL's.** It drifts about 0.25 s an hour. Use `ros/tools/clock_offset.py` (`serve` in WSL, `probe 192.168.0.100` on the Pi, then `sudo -n date -s @<t>`), plus ~43 ms for sudo's start-up; re-probe to within ~1 ms.
- Baseline to beat (P9, Nov 2, `nav_profile:=pi`, single run): route 15/16 goals, localization median 0.16 m, 2 laps 429 s, tidy 5/6 toys binned. Pi ~2.83 cores holding (arm_node 0.58 of a core), ~3.89 on the route (arm_node 0.47), busiest core p95 100%.
- Check that the arm works in the sim on the PC first (`python -m pytest -q ros/src/omni_arm/test`, the omni_cpp parity tests, v11's arm checks in `simulation/v11 sil/test_v11.py`, a tidy through `ros/omni.sh arm`). Then measure on the Pi. Report single runs as single runs.
