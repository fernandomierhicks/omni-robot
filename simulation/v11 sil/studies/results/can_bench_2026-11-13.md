# Two AK40-10s on CAN through the robot's firmware: timing, response, telemetry (Nov 13, 2026)

**Hardware measurement**, wheels up. Two CubeMars AK40-10 V3.0 KV170 in servo mode (CAN ids 1 and 2, 1 Mbit/s,
500 Hz status broadcast, 100 ms timeout), **motor 1 bare, motor 2 with the `cad/v13` omni wheel**, 24 V bench supply.
The robot's **baseline firmware**, unchanged: Teensy 4.1, env `arm_bench`, protocol 9, build `aea161e4`, on the Pi 4's
USB under the robot step (`mcu_link`, `mode_manager`, console). Profiles through the console's motor test, recorded at
the MCU's 200 Hz STATE by `ros/tools/wheel_capture.py`; analysed by `studies/can_bench.py`
(`can_bench_2026-11-13.json`). Raw captures (outside Dropbox): `C:/Users/ferna/bench_data/can_2026-11-13/`.
Protocol facts: the CubeMars **AK Series V3.0 Module Product Manual** (V3.0.0, cubemars.com), sections 3.1.1 and 4.3.

## The path and its rates

| Link | Rate | Set by |
| --- | --- | --- |
| Robot computer → MCU (CMD) | 100 Hz (it is also the heartbeat) | `mcu_link` / protocol |
| MCU → each motor (velocity frame) | **250 Hz**: one CAN frame a 1 ms tick, round robin over 4 wheels | firmware (`drive_motors`) |
| Motor → MCU (status broadcast) | **500 Hz**, the motor's ceiling (the tool allows 1–500 Hz) | CubeMars tool |
| MCU → robot computer (STATE) | 200 Hz; USB round trip 0.23 ms | firmware (`STATE_PERIOD_US`) |

- **STATE stream on the Pi:** 0 samples missing in ~120 s of steady capture (24k samples, every gap exactly 5.0 ms).
  The only gaps (25–30 ms) came in a new subscriber's first 0.25 s, and DDS matching on the Pi took up to ~2.5 s:
  `wheel_capture.py` started two profiles before its subscription saw anything and lost their start (`tri_m1`,
  `steps_m2`). Fixed: it now waits for live STATE first.
- **CAN bus load** (an 8-byte extended frame is 131 bits + stuffing, ~140 µs at 1 Mbit/s): four motors at the
  baseline = 1000 commands + 2000 status frames a second ≈ **42 %**; this bench (two motors) ≈ 28 %. Every motor
  every tick would be 6000 frames/s ≈ 84 %: too close to full. Two frames a tick (each motor at 500 Hz) ≈ 56 %.

## Response

| | Motor 1 (bare) | Motor 2 (wheel) |
| --- | --- | --- |
| Acceleration cap (servo velocity mode, any asked ramp) | 150 rad/s² | 148 rad/s² |
| Step to 20 rad/s: time to 90 % / overshoot | 0.13 s / 0.25–0.5 rad/s | 0.13 s / 0.46–0.61 rad/s |
| Reversal −20 → +20 rad/s, time to 90 % | 0.25 s | 0.25 s |
| **Lag behind the asked speed on a 50 rad/s² ramp** | **8.6 ms** | **9.0 ms** |
| Start from rest: asked → speed ramp onset (2000 rad/s² ask) | 13.2 ms (n 9) | 13.4 ms (n 15) |
| J/k (current per rad/s² of acceleration) | 2.06 mA s²/rad | 3.86 mA s²/rad |
| Friction current at steady speed | 0.089 + 0.0022 \|ω\| A | 0.077 + 0.0035 \|ω\| A |
| Speed ripple at a steady speed (sd) | 0.09 rad/s | 0.08 rad/s |
| At rest: current offset / noise (sd) | −0.069 / 0.012 A | −0.048 / 0.015 A |

- **~5.5 ms inside the motor (the new finding).** The sim's own path (the firmware's round robin, a 500 Hz status read
  1.5 ms old on average, its speed loop with the 148 rad/s² ramp) lags the same ramps by 3.2–3.6 ms; the bench by
  8.6–9.0. A pure delay of **5.5 ms** fits motor 2's ramps (rms 0.12 rad/s) and 5.5–7.5 ms its steps. (Motor 1's
  triangle capture started mid-profile, so its fit is invalid; its ramp lag, 8.6 ms, agrees.) From the host it can't be
  told whether the motor acts late or reports late; it is applied on the command side in the sim (below).
- **Mean budget, wheels up, firmware ramp → STATE sees the speed respond (~9 ms):** round-robin wait 1.5 (0–3) +
  frame 0.15 + **motor 5.5** + speed loop ~0.5 + status age ~1.2 (0–2) + tick pickup ~0.5. From a ROS command add the
  CMD period (0–10 ms, mean 5). Commanding each motor every 2 ms (two frames a tick) would save ~0.5 ms of mean
  latency; every 1 ms ~1 ms, at a bus load we shouldn't run. The motor's own 5.5 ms dominates.
- **Torque per amp ≈ 0.48 N m/A of the reported current (inference, VERIFY).** The bare motor's J/k (2.06 mA s²/rad)
  against the datasheet's rotor (97.35 g cm², ×10² reflected = 0.97e-3 kg m²) gives 0.47 N m/A, the firmware's
  `AK_KT` (gearbox inertia ignored, so if anything a little higher). The wheel adds 1.80 mA s²/rad, 0.87e-3 kg m² at
  0.48: the sim's wheel 0.91e-3. So the earlier bench's "+51 % inertia" (wheel_bench_2026-11-13 finding 4) was the
  torque per amp, not the inertia: the sim's inertia is right at 0.48. The sim's drive model uses 0.73 N m/A
  internally (the chart fit) while its motor reports current through 0.48, the same as the bench: so the reported
  currents agree, but the model's current limit and heating may be ~1.5× optimistic per N m (0.73 / 0.48 ≈ 3/2, the
  factor between the two Park conventions). Settle with a known mass on the hub (wheel_bench report, "More to
  explore").
- Friction and the 148 rad/s² cap reproduce the earlier single-motor bench on a second motor; top speed couldn't be
  re-measured (the firmware now caps at 37.2 rad/s; both reached it with 0.4–0.8 rad/s overshoot).

## Telemetry content and resolution (servo-mode status, manual 4.3.1)

- Position 0.1° (int16: wraps at ±3276.8°, ~9 output turns: ~1.5 s at full speed; the firmware unwraps it),
  speed 10 ERPM = **0.0068 rad/s** at the output (reads exactly 0 at rest), current **0.01 A**, temperature 1 °C,
  error code.
- **The temperature is the driver board's, not the winding's** (manual 4.3.1). The firmware copies it into both the
  "rotor" and "MOSFET" fields and the console shows it as the motor's; here 48 and 54 °C after ~20 min idle on the bench.
  The winding's temperature is only on the motor's UART.
- **Bus voltage: not on CAN.** Servo and MIT replies carry none; the CAN side only says over/under-voltage through the
  error code. The motor's **UART** has it (`COMM_GET_VALUES` 0x45, input voltage /10 V, plus input current, MOSFET and
  motor temperatures), on the connector whose GND the CAN link already uses. Reading it would take a UART per motor to
  the Teensy (3.3 V, set on the driver). The robot reads the pack on the Teensy's A17 divider instead (the bench build
  reports a fixed 24 V).

## Options found (not tried)

- **Query-reply mode** (the tool's other CAN port mode): the motor answers each command with one status frame instead
  of broadcasting. Status then comes right after each command at the command's rate, its age known; same bus load as
  now at 250 Hz a motor. Set in the CubeMars tool (Fernando, at the PC); the firmware would need no change to try it
  (it already takes every status frame it gets), but the feedback timeout (50 ms) and odometry rate follow the
  command rate.
- **Position-velocity mode** takes an explicit acceleration (to 327,670 ERPM/s ≈ 234 rad/s² at the output); velocity
  mode uses a fixed default (the measured ~148 rad/s²). Not needed: the robot asks ≤ ~74 rad/s².

## Applied to the sim (Nov 13)

`sil_robot.AkMotor` takes `latency`: a command frame takes effect that long after it arrives (the link's timeout still
counts from the arrival). `SilRobot(ak_latency=AK_LATENCY)`, **5.5 ms**; `ak_latency=0` reproduces runs before
Nov 13. The SIL robot on the floor (four wheels on the same triangle, spinning in place) lags 5.4 ms without it and
10.8 ms with it; wheels up the sim's 3.5 ms + 5.5 matches the bench's 8.6–9.0. All of `test_v11.py` passes (153).
The direct-physics studies (no SIL) don't see it. Status rate 500 Hz and the acceleration cap were already modelled.
