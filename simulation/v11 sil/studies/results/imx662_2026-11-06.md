# A forward IMX662 USB 2 camera at the nose (Nov 5–6 2026, sim + CAD study, proposal)

Fernando's brief: a generic IMX662 USB 2 camera (Arducam-sized) as the arm robot's general forward-looking camera, on the bottom deck
under the lidar, tilted up, for people, things and AprilTags (the IMX662 sees near-infrared too). No full CAD, a generic STEP to see it
fits; then try tag detection and optical flow, with the rolling shutter rendered, to see whether it helps the robot navigate faster.

Robot: current `ARM_D435` with the D435 on the arm riser (`robot_export.D435_RISER`, 30° down, baselined Nov 5). The camera is added
at run time (`imx662_cam.with_camera`); `robot_export` and the bridge are unchanged.

## The camera (generic, every number VERIFY on the module bought)

| Item | Value |
| --- | --- |
| Sensor | Sony IMX662 (STARVIS 2), 1/2.8", 1920 × 1080, 2.9 µm, **rolling shutter**, NIR-sensitive |
| Module | 38 × 38 mm board, M12 lens holder, Ø14 × 16 mm M12 lens, USB-C on the back with a straight plug (Arducam-sized; generic) |
| Lens | 2.8 mm: 89.6 × 58.4° (pinhole; real wide M12 lenses barrel-distort and are rectified first) |
| Link | UVC MJPEG over USB 2 at 30 fps (raw 1080p30 YUY2 does not fit USB 2); JPEG quality 85 **(est)** |
| Readout (first → last row) | 16 ms (a 60 fps sensor mode) to 33 ms (the whole frame time) **(est)**; 0 = global-shutter reference |
| Exposure | 4 ms (bright room), 12 ms (dim) **(est)** |
| Noise | 4000 e⁻ full scale, 1.5 e⁻ read, 12-bit, 30 % vignetting **(est)** |

## 3. Tags while moving (`imx662_study.py frames`, `imx662_detect.py tags`)

The furnished house's tag faces were repainted in the model with their real 36h11 codes (the png placeholders are untouched). Each tag
was faced from 1.5 and 3 m where the robot fits (46 poses, 37 tags visible in the still frames). Each pose was rendered still and
passing the pose at speed, through the rolling shutter (`imx662_cam`: the scene re-rendered every 0.5 ms across readout + exposure,
each row averaging the renders in its own exposure window, so blur and skew are exact to 0.5 ms), the sensor noise and MJPEG.
Detection used pupil-apriltags (the C library proposed in 4.6) with the `min_margin` 30 gate. Recall is against the still
global-shutter frame from the same pose. The position error is against the truth at the frame's middle row.

**4 ms exposure** — recall / position error p50 (p90), % of range / orientation flips / wrong ids:

| Motion | GS (0 ms) | 16 ms readout | 33 ms readout |
| --- | --- | --- | --- |
| still | 1.00 / 1.01 (1.26) / 3 / 0 | 1.00 / 0.99 (1.27) / 3 / 0 | 1.00 / 0.97 (1.29) / 2 / 0 |
| forward 0.5 m/s | 1.00 / 0.91 (1.26) / 4 / 0 | 1.00 / 0.80 (1.15) / 3 / 0 | 1.00 / 0.57 (1.00) / 3 / 0 |
| forward 1 m/s | 1.00 / 0.86 (1.30) / 4 / 0 | 1.00 / 0.58 (1.05) / 4 / 0 | 1.00 / 0.81 (1.15) / 4 / 0 |
| forward 2 m/s | 1.00 / 0.75 (1.16) / 5 / 0 | 1.00 / 0.91 (1.47) / 5 / 0 | 1.00 / **2.39 (3.18)** / 4 / 0 |
| sideways 1 m/s | 1.00 / 0.55 (1.20) / 3 / 0 | 1.00 / 0.90 (1.35) / 3 / 0 | 1.00 / **1.51 (1.75)** / 2 / 0 |
| spin 60°/s | 1.00 / 0.85 (1.99) / 4 / 0 | 1.00 / 1.56 (2.34) / 5 / 0 | 0.97 / **2.58 (2.77)** / 4 / 0 |
| spin 120°/s | **0.62** / 4.45 (6.38) / 0 / 0 | 0.65 / 5.02 (5.89) / 1 / 0 | 0.65 / 6.25 (7.11) / 1 / 0 |
| spin 180°/s | **0.32** / 8.56 (8.65) / 0 / 0 | 0.32 / 9.08 (9.14) / 0 / 0 | 0.35 / 11.0 (11.1) / 0 / 0 |
| forward 1 m/s + 0.5° pitch wobble at 8 Hz | 1.00 / 0.82 (1.15) / 5 / 0 | 1.00 / 0.91 (1.56) / 3 / 0 | 1.00 / 1.39 (2.47) / 0 / 0 |

**12 ms exposure (dim room):** spins of 120°/s and faster decode nothing; forward 2 m/s keeps 86–89 %; the wobble case 73–78 %;
sideways 1 m/s keeps every tag at 2.2–2.8 % range error (p50). Full table: `results/imx662/summary.md`.

- **The rolling shutter does not cost detections; motion blur does.** Recall is the same at 0, 16 and 33 ms readout in every motion. It
  falls only with blur: spins ≥ 120°/s at 4 ms, any spin at 12 ms.
- **The rolling shutter costs pose accuracy under motion**, about 2–3× at 33 ms readout: 2.4 % of range at 2 m/s (≈ 4–7 cm at 1.5–3 m),
  1.5 % sideways at 1 m/s, 2.6 % spinning at 60°/s. At 16 ms it stays within ~1.6 %. Knowing each row's time, a rolling-shutter-aware
  pose (or de-skewing with the gyro) would remove most of it; not tried.
- **No wrong ids** in ~3,700 detections. Orientation flips (the planar pose ambiguity's other solution, ~10 % of detections, the same
  still) need the graph's existing gates.
- The ~1 % still error is common to every readout: the sim's tag/pixel conventions and MJPEG, not the shutter.
- Cost on the PC (one core = Windows PC, not the robot computer): MJPEG decode 2.7 ms; detection 37 ms (1 thread) / 25 ms (2) at full
  resolution, 15 / 10 ms with `quad_decimate` 2, which found the same tags in these frames.

## 4. Optical flow (`imx662_study.py flow`, `imx662_detect.py flow`)

Twelve frames at 30 fps from 4 open-floor starts per motion. Shi-Tomasi corners with pyramidal LK (forward-backward checked), then the
essential matrix and its rotation and translation direction against the truth.

Yaw-rate error °/s p50 / direction-of-travel error ° p50 / failed pairs of 44:

| Motion | GS (0 ms) | 16 ms | 33 ms |
| --- | --- | --- | --- |
| forward 0.5 m/s | 1.6 / 121 / 8 | 2.0 / 79 / 6 | 1.5 / 9 / 3 |
| forward 1 m/s | 2.0 / 8 / 2 | 1.6 / 11 / 4 | 1.5 / 7 / 3 |
| forward 2 m/s | 2.2 / 3 / 0 | 1.6 / 3 / 0 | 1.5 / 3 / 0 |
| sideways 1 m/s | 1.7 / 3 / 6 | 1.2 / 3 / 10 | 1.9 / 3 / 7 |
| spin 60°/s | 2.7 / – / 1 | 3.1 / – / 2 | 3.7 / – / 0 |
| spin 180°/s | 101 / – / 11 | 54 / – / 9 | 35 / – / 5 |
| forward 1 m/s + wobble | 2.9 / 8 / 2 | **8.6 / 36** / 3 | **16.6 / 52** / 2 |

(Spins move the camera ~7 mm a frame, so their travel direction is meaningless.)

- **Yaw rate from flow (1.5–4°/s error) is worse than the BNO085's gyro**, and it breaks at 180°/s: ~100 px a frame and too few
  tracks.
- **Direction of travel to ~3° at ≥ 1 m/s** (forward or sideways) is a possible wheel-slip check for the omni base. At 0.5 m/s, and
  in far, low-texture views, the baseline is too short (sign flips).
- **Rolling shutter + pod wobble is the real problem:** 0.5° at 8 Hz takes the yaw-rate error 2.9 → 8.6 → 16.6°/s and the direction
  error 8 → 36 → 52° from GS to 16 to 33 ms. Smooth motion alone barely shows the shutter.
- The sim's surfaces are smooth renders (little texture), so real track counts will differ; the geometric effects (shutter, wobble,
  parallax) are what transfer.

## Answer: does it help the robot go faster?

- **Tags: yes, as absolute fixes while driving.** This camera sees a wall tag from 88 % of house poses where the riser D435 sees none.
  With a 4 ms exposure it decodes every tag the still frame does at up to 2 m/s forward or 1 m/s sideways, at 1–2.4 % of range,
  without wrong ids. That is the anchor that would let localization hold at higher speed (`nav_profile:=pi`'s 0.16 m drift, slips at
  speed: 4.10). Keep spins at or under ~60–90°/s (or the exposure short) when a tag fix matters. A 16 ms readout mode is worth asking
  the module for.
- **Optical flow: no, not as a speed lever.** Its rotation is worse than the gyro and fails on fast spins. Its translation direction
  needs ≥ 1 m/s and degrades badly with rolling shutter and pod wobble. The lidar scan matching already gives the same information.
  At most a slip monitor; not worth building now.
- **People:** a standing adult is whole in the picture from 1.46 m (20° up); the riser D435 never sees above knee height. NIR with an
  850 nm lamp (dark rooms) is not modelled: the renders are visible light.

## Not modelled / open

Lens distortion and its rectification; auto exposure and flicker (50/60 Hz lights band a rolling shutter); the module's real readout,
exposure range, MJPEG quality and USB latency; real textures and lighting; NIR; detection on the robot computer; the stand (placeholder),
the module's mounting holes and the plug (VERIFY on the module); single renders per pose (no seeds beyond the sensor noise).
