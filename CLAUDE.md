# omni-robot (play-catch kiwi robot)

Read `design.md` first. It is the single source of truth, kept short: the current design, its expected performance from simulation, findings from non-adopted designs, sim strategy and options, where things live, run commands, next steps and a condensed decision log. `design full history.md` is the full 2,800-line history; every "design.md section N" / "§N" reference below and in the code comments points there (the numbering is only kept in the history file). Don't edit the history file. Superseded documents live in `archive/`; don't edit them or start parallel design docs. When the design changes, update the matching `design.md` section, its decision log and the "Start here" status.

- Python: use `C:\Users\ferna\.venvs\omni-robot-sim\Scripts\python.exe` (MuJoCo, build123d). `python` on PATH is PlatformIO's interpreter; never install into it.
- The current sim is `simulation/v2 detailed physics`. Check `python -m pytest -q` there after changes. Part data lives in `catalog.py`, the fitted configuration in `params.py`.
- `simulation/v3 compact` is a proposed compact redesign (4-wheel X base, tilting catch/launch module; `design.md` section 20). It stays "proposed" until Fernando adopts it; its tests are `test_v3.py`.
- `simulation/v5 unlimited` is an exploration on top of v3b (`design.md` section 21): no firmware limits by default (`limits="firmware"` restores them), a per-pixel vision model, and a hopper mode. Its tests are `test_v5.py`.
- `simulation/v6 shallow throw` builds on v5 for throwers 6-7 m away (`design.md` section 22): chute feed (floor sloping into the nip of two driven feed wheels, J-bend to the flywheels, one ball per trigger; round 1 roller feed kept), padded pocket, 35° catch tilt, honest stereo track start, ceiling-aware returns, tube/indexer hopper options. Round 3 (`design.md` section 23): GM3506 feed motors modeled from datasheets, viscoelastic contacts (`contact_model.py`), randomized worlds (`randomize.py`), rolling resistance / friction fields / thresholds / carpet (`floor.py`), a motor study. Proposed; its tests are `test_v6.py`.
- `database/` is the shared actuator database (`design.md` section 24): motors, servos, controllers and sources as CSV, with `actuator_db.py` (validate, gaps, sim export). Every value carries provenance and a source; run `python actuator_db.py validate` and `python -m pytest -q` there after edits. It will move up to `Robotics/database/`, so keep it free of omni-robot imports. `studies/actuator_choice.py` applies it to this robot.
- `simulation/v7 home floor` builds on v6 round 3 for home floors (`design.md` section 25): big-roller printed omni wheels, sprung wheel pods, terrain-aware firmware (edge map), mecanum and swing-pod options, and `house.py`, a house you drive with the keyboard, a gamepad or a flight stick (pygame). `SimParams()` still builds v6; the proposal is `house.BASES["v7"]`. Crossings must use `wheel_model="rollers"`. Proposed; its tests are `test_v7.py`.
- `simulation/v8 swerve` is v7 plus three- and four-module swerve bases (`layout="swerve3"`, `design.md` section 26): steered tyred modules with ST3215-HS steering servos, `SwerveKinematics`, pods retuned for three wheels, part S of `studies/home_floor.py`. Exploration: v7 stays the catch base. Its `house.py` defaults to the swerve. Its tests are `test_v8.py`.
- `simulation/v9 sensors` is v8 plus sensor models (`sensors.py`: ICM-42688-P IMU, encoders, PAA5100JE flow, RPLIDAR C1 ray-cast scans) and localization (`estimator.py`: EKF, map scan matcher, shadow-mode `Localizer`), `design.md` section 27. Step 1 of the move to ROS-like simulation; step 2 is a ROS 2 bridge in WSL2, keeping MuJoCo's physics. Its tests are `test_v9.py`.
- `simulation/v10 ros bridge` is the sim side of v10 (`design.md` section 28): v9 + `bridge_core.py` (no ROS), A2M12 / BNO085 sensor models, `map_quality.py`. Its tests are `test_v10.py` (Windows or `ros/omni.sh test`).
- `simulation/v11 sil` is v10 with the robot's own code in the loop (`design.md` section 30): the MCU firmware (`firmware/`, C++, Teensy 4.1) ticked every 1 ms by `sil_robot.SilRobot` (software in the loop), and the Jetson's catch code (`ros/src/omni_catch`, `omni_mcu`) in one process (`sil_game.py`) or as ROS nodes (`ros/omni.sh catch`). `robot_export.py` generates `firmware/lib/omni_fw/fw_params.h` and `omni_catch/config/robot_v11.json` from `SimParams`: rerun it after a params / catalog / model change (a test checks they're current). Its tests are `test_v11.py` (v10's + the firmware and catch code). It's the default sim for `ros/omni.sh` (`firmware:=false` is v10's bridge). Section 31: `scene="house"` (`house_scene.py`, a furnished house around the field; decoration only, the same physics) and `frames="rendered"` (`rendered_camera.py`, MuJoCo renders through a camera sensor model, sim time only) in `catch_world.WorldConfig` / `sil_game.py --scene --frames`; the defaults (arena, sparse) reproduce earlier results. The house's CC0 textures come from `python house_scene.py fetch` (not in git).
- `firmware/` is the MCU's code: `lib/omni_fw` (board-free core: the same source runs on the Teensy and in the sim), `src/main.cpp` (Teensy drivers), `sil/` (the SIL library: zig c++ on Windows, g++ in WSL, built on demand). Build for the Teensy with PlatformIO (`pio run` in `firmware/`); the pin map in `board_teensy41.h` is checked by `static_assert`s (PINS.md). Keep the core free of Arduino includes; change `protocol.h` and `ros/src/omni_mcu/omni_mcu/protocol.py` together. Flashing only in attended sessions.
- `ros/` (repo root, monorepo) is the robot's ROS 2 software: `omni_bringup`, `omni_perception`, `omni_interfaces`, `omni_mcu`, `omni_catch` (they go to the Jetson; `omni_catch` / `omni_mcu` keep ROS-free cores the sim imports) and `omni_sim` (PC only: the MuJoCo bridges, the firmware's USB port, viewer, scoring). Keep robot packages free of `omni_sim` imports. The ROS side runs in WSL (`wsl -d Ubuntu-24.04`); always go through `ros/omni.sh <step>`, which mirrors `ros/src` and the sim into `~/omni_ws` (ext4) and builds there; never build on `/mnt/c`. WSL's Python is `~/.venvs/omni-ros`. Don't draw MuJoCo inside WSL (D3D12 translation ~0.8 s/frame, llvmpipe eats the sim's CPU): the 3D view is `ros/tools/mujoco_view.py` on Windows, fed by the bridge over localhost. Run several ROS runs at once on separate `ROS_DOMAIN_ID`s. `Launcher.cmd` (root) is Fernando's button launcher (`launcher.ps1`, WinForms); keep it working when steps change.
- `ros/src/omni_console` is the operator console (`design.md` section 2, phase 1). It goes to the Jetson.
  - **Pieces:** `missions.py` and `status.py` are ROS-free; `mission_node` and `console_web` are the nodes; `web/` is the page, plain ES-module JS with no build step. `web/vendor/README.md` lists the vendored libraries.
  - **How the page connects:** through rosbridge, using `/console/*` topics and the one `/console/command` service. Add new features as verbs plus settings in `missions.py`, not new service types. Never stream raw high-rate topics or images through rosbridge.
  - **Launch:** the interactive steps start it (`console:=false` turns it off). Don't run console nodes on sim time: the 1 kHz `/clock` costs a Python node most of a core.
  - **Tests:** `& $py -m pytest -q ros/src/omni_console/test`. End to end: `ros/tools/console_smoke.py` against a running `nav` step.
  - **Running alongside Fernando's stack:** use another `ROS_DOMAIN_ID` plus `mcu_port:=5771`, and stop only your own launch, not `omni.sh stop`.
- Jetson caveat (VERIFY): the Orin's JetPack 6 is Ubuntu 22.04 and the stack is ROS 2 Jazzy (24.04): Docker on the Orin, or a JetPack 7 for Orin if it exists.
- CAD is in `cad/`. Dimensions come from the sim through `dims.py`. After CAD changes, run `build.py` (it must still report 0 clashes) and `render.py`. `cad/` is the v2 robot; `cad/v7/` is the current robot to the fastener level (`design.md` section 29): its `build.py` checks clashes at every tilt and suspension state and writes BOM.md / PRINT_LIST.md; renders need `build.py --render-only` first.
- CAD fasteners (Fernando): no heat-set inserts; M3 screws thread-form into 2.8 mm printed holes (≥ 6 mm engagement, checked per screw by `cad/v7/build.py`), 3.4 mm through holes; M3 wherever possible; pan and flat heads only (no socket heads). View `cad/v7` with `view.py`; `step_export.py` writes the SolidWorks STEP.
- Parts are 3D printed wherever possible (PLA, PETG, TPU; ~256 mm bed).
- Values marked (est) or VERIFY are unconfirmed. Don't present them as measured.
